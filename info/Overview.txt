### Secure Credentials Sharing App: Comprehensive Implementation Overview

**I. Core Security Principles & Architecture**

Your application is designed around a robust End-to-End Encryption (E2EE) model, ensuring that the server never has access to the plaintext sensitive data (credentials).

* **End-to-End Encryption (E2EE):** All sensitive credential data is encrypted on the sender's client and decrypted only on the recipient's client. The server acts as a secure relay for encrypted blobs.
* **Hybrid Key Model:**
    * **Long-Term Identity Key Pair:** This key pair identifies a user permanently. Its public component is stored on the server as a **digitally signed certificate**, and its private component is managed by the user outside the browser. Used for offline messaging and digital signatures.
    * **Ephemeral Session Key Pair:** This key pair is generated fresh for each browser session. Its public component is temporarily uploaded to the server, and its private component lives only in the browser's memory. Used for online, active session messaging.
* **Organizational Certificate Authority (CA):** Your organization will run an internal CA to sign all user's Long-Term Public Identity Keys, binding them into trusted digital certificates. This is crucial for **preventing Man-in-the-Middle (MITM) attacks** during public key exchange.
* **Digital Signatures for Integrity & Authenticity:** Every message will be digitally signed by the sender using their Long-Term Private Identity Key. This ensures:
    * **Integrity:** The message has not been tampered with in transit.
    * **Authenticity:** The message genuinely originated from the claimed sender.
* **Local Hosting:** Provides organizations complete control over their data, network, and application environment, crucial for sensitive data.
* **Data Minimization:** Encrypted messages are deleted from the server once successfully fetched by the recipient.

### II. Server-Side Implementation (Flask API & Database)

This covers the backend logic and data storage.

1.  **Foundational API Security:**
    * **User Authentication:**
        * Secure storage of user passwords using strong, salted hashing (e.g., `bcrypt`, Argon2).
        * **JWT Access Token Generation:** Issue short-lived (1-hour expiry) JWTs upon successful login.
        * **JWT Blacklisting/Revocation:** Implement a mechanism (e.g., a Redis cache of invalid tokens) to immediately invalidate JWTs upon user logout or session expiry.
        * **Secure Secret Key:** Use a very strong, randomly generated `JWT_SECRET_KEY` stored securely (e.g., environment variable, not in code).
        * **Rate Limiting:** Protect login, registration, and other critical endpoints against brute-force/DoS attacks.
        * **HTTPS Enforcement:** All API traffic must be over HTTPS in production.
    * **Input Validation:** Strict validation for *all* incoming data (JSON payloads, URL parameters) for types, lengths, and formats (e.g., PEM strings, UUIDs). Reject malformed requests early.
    * **Error Handling:** Provide generic, non-informative error messages to clients (e.g., 400, 401, 403, 404, 500 without stack traces).
    * **Secure Configuration:** Ensure `FLASK_DEBUG=False` in production. All sensitive configuration (database credentials, secrets) must be externalized (environment variables).
    * **CORS:** Implement strict Cross-Origin Resource Sharing (CORS) policies to allow requests only from your legitimate frontend domain.

2.  **Key Management System:**
    * **Database Schema Updates:**
        * **`User` Model:** Add a field to store the user's **signed Long-Term Public Identity Certificate** (PEM string) and its associated `key_uid`.
        * **New `EphemeralPublicKey` Model/Table:** To store the `ephemeral_public_key` (PEM string), its `key_uid`, a `user_id`, and a `jti` (JWT ID) to link it to the specific active session.
    * **API Endpoint: `POST /api/user/register_long_term_key`:**
        * Allows a user (after initial authentication) to upload their newly generated raw Long-Term Public Identity Key.
        * **Internal Call to CA Module:** This endpoint will internally call the CA module to sign this public key and generate the X.509 certificate.
        * Stores the **signed certificate** in the User model.
        * Requires strong validation of the incoming public key format.
    * **API Endpoint: `POST /api/user/set_ephemeral_key`:**
        * Allows a user to upload their current session's Ephemeral Public Key.
        * Stores it in the `EphemeralPublicKey` table, linked to the current user and JWT `jti`.
        * Requires strong validation of the incoming public key format.
    * **API Endpoint: `GET /api/user/public_key/<username>`:** **(Critical for MITM prevention)**
        * Authenticated endpoint.
        * **Key Discovery Logic:**
            1.  Check if `<username>` has an **active `ephemeral_public_key`** linked to a current session (by checking against JWT blacklist/expiry for the `jti`).
            2.  If an active ephemeral key exists, return its **raw public key (PEM string)** and a type indicator (`"ephemeral"`).
            3.  If no active ephemeral key, return the user's **signed Long-Term Public Identity Certificate** (PEM string) and a type indicator (`"identity"`).
        * Handle cases where the user or key is not found (e.g., 404 Not Found).
    * **Ephemeral Key Lifecycle Management:** Implement a mechanism (e.g., a background job, or triggered by JWT blacklisting) to **delete `ephemeral_public_keys` from the database** as soon as their associated JWT session expires or is blacklisted.

3.  **Organizational Certificate Authority (CA) Module:**
    * **CA Key Pair Management:**
        * A one-time, highly secure process to generate the organization's **root CA private key** (e.g., stored offline, in an HSM).
        * Generate the corresponding **CA Public Certificate** (self-signed). This certificate needs to be distributed securely to all client applications (e.g., bundled, or fetched once over a trusted out-of-band channel).
    * **Certificate Issuance Logic:**
        * When `POST /api/user/register_long_term_key` is called, this module takes the raw user public key.
        * Generates an X.509 digital certificate embedding the user's public key, user ID/name, and a validity period.
        * **Signs this certificate using the CA's private key.**
        * Returns the signed certificate (PEM format) to the calling endpoint for storage.
    * **Certificate Revocation (Optional but Recommended for High Security):**
        * Implement a system for generating and distributing Certificate Revocation Lists (CRLs) or an Online Certificate Status Protocol (OCSP) responder. This allows marking compromised Long-Term Identity Certificates as invalid.

4.  **Message Management System:**
    * **`Message` Database Model:**
        * `sender_id`, `recipient_id`.
        * `encrypted_content` (the ciphertext of the credential).
        * `recipient_key_uid`: Identifier for the specific public key (ephemeral or long-term identity) used to encrypt for the recipient.
        * `sender_signature`: The digital signature of the plaintext message, created by the sender's Long-Term Private Identity Key.
        * `sender_public_identity_key_uid`: Identifier for the sender's Long-Term Public Identity Key (from their certificate), used by the recipient for signature verification.
        * `timestamp`.
        * `is_opened` (Boolean, defaults to `False`).
    * **API Endpoint: `POST /api/messages/send`:**
        * Authenticated endpoint.
        * Accepts `recipient_username`, `encrypted_content`, `recipient_key_uid`, `sender_signature`, and `sender_public_identity_key_uid`.
        * Stores the message in the database.
        * **No decryption or modification** of `encrypted_content` on the server.
    * **API Endpoint: `GET /api/messages/inbox`:**
        * Authenticated endpoint.
        * Retrieves all messages where `recipient_id` matches the current user.
        * Provides options to filter by `is_opened=False` (unopened messages).
        * **Crucially:** Marks fetched messages as `is_opened=True` *after* successful retrieval, indicating they have been processed by the client.
    * **API Endpoint: `DELETE /api/messages/<message_id>`:**
        * Authenticated endpoint.
        * **Access Control:** Ensure only the `recipient_id` (or authorized admin) can delete the message.
        * Deletes the message from the database. (Alternative: Delete messages automatically after retrieval via `GET /inbox` to minimize server storage of encrypted data).

### III. Client-Side Implementation (Web Application - JavaScript)

This covers the frontend application logic that runs in the user's browser.

1.  **User Authentication Flow:**
    * Login form to send username/password to the server.
    * Receive and securely store the JWT (e.g., in `sessionStorage` or `localStorage` - but be extremely aware of XSS risks if using `localStorage`). Include JWT in `Authorization` header for all API calls.

2.  **Key Pair Generation:**
    * **Long-Term Identity Key Pair Generation:**
        * UI to guide users through initial generation (e.g., at first login or profile setup).
        * Use **`Web Crypto API`** (recommended) or a well-vetted JavaScript cryptographic library (e.g., `jsencrypt` for RSA, `elliptic` for ECC).
        * **Crucial:** Prompt the user to **download their generated Long-Term Private Identity Key as an encrypted file** (e.g., PEM format encrypted with a strong passphrase chosen by the user).
        * Send the **raw Long-Term Public Identity Key** to `POST /api/user/register_long_term_key` for server-side CA signing.
    * **Ephemeral Session Key Pair Generation:**
        * Automatically generate a new ephemeral key pair **immediately upon successful user login**.
        * Store the **Ephemeral Private Key ONLY in browser memory** for the duration of the session.
        * Send the **Ephemeral Public Key** to `POST /api/user/set_ephemeral_key`.

3.  **Key Management (Client-Side Memory & Storage):**
    * **Organizational CA Public Certificate:** This must be **bundled directly with your client-side application** (e.g., hardcoded, or part of your build process) as the trusted root for certificate validation.
    * **Long-Term Private Identity Key Management:**
        * UI for users to **load/import** their encrypted Long-Term Private Identity Key (e.g., file upload and passphrase input) when required.
        * Once loaded, decrypt the key and hold it in **browser memory only for the specific operation**, then **immediately purge it from memory**.
    * **Ephemeral Private Key Purging:**
        * Ensure the **Ephemeral Private Key is purged from browser memory immediately on user logout or session expiry**.

4.  **Message Sending Flow:**
    * **Recipient Public Key Fetching:** Call `GET /api/user/public_key/<recipient_username>`.
    * **Certificate Validation (for Long-Term Keys):** If the server returns a signed certificate for the recipient's identity key:
        1.  Parse the X.509 certificate.
        2.  **Verify the certificate's signature** using the **bundled Organizational CA Public Certificate**.
        3.  Check the certificate's **validity period**.
        4.  (If implemented) Check **revocation status** (CRL/OCSP).
        5.  If *all validation steps pass*, extract the recipient's public key from the certificate. **If validation fails, abort the send process and alert the user.**
    * **Digital Signature Generation:**
        1.  Hash the *plaintext* credential content (e.g., SHA-256).
        2.  **Sign this hash using the sender's *loaded Long-Term Private Identity Key***. (This means the sender will need to load their key into memory for every send operation).
    * **Encryption:** Encrypt the *plaintext* credential content using the *validated recipient's public key* (either ephemeral or long-term identity).
    * **API Call:** Send the `encrypted_content`, `recipient_key_uid` (from the server's response), `sender_signature`, and `sender_public_identity_key_uid` (from the sender's loaded identity key) to `POST /api/messages/send`.

5.  **Message Receiving & Decryption Flow:**
    * **Message Fetching:** Call `GET /api/messages/inbox` on login and periodically.
    * **Decryption Logic (Per Message):**
        1.  Examine the message's `recipient_key_uid` metadata.
        2.  If `recipient_key_uid` matches the **current session's in-memory ephemeral private key**, use it to decrypt the message.
        3.  If `recipient_key_uid` matches one of the user's **Long-Term Public Identity Keys**, prompt the user to **load their Long-Term Private Identity Key** into memory for decryption.
        4.  Once decrypted, retrieve the `sender_signature` and `sender_public_identity_key_uid` from the message.
        5.  Fetch the sender's **Long-Term Public Identity Certificate** (using `sender_public_identity_key_uid`) from `GET /api/user/public_key/<sender_username>`.
        6.  **Verify Sender's Certificate:** Perform the same certificate validation steps as in the sending flow (signature, validity, revocation) using the bundled Organizational CA Public Certificate.
        7.  **Verify Digital Signature:** Hash the *decrypted plaintext* content. Use the sender's public key (extracted from the *validated* certificate) to verify this hash against the `sender_signature`.
        8.  **Crucial Action on Failure:** If *any* certificate validation or signature verification step fails, **DO NOT display the message content to the user**. Alert them about potential tampering or an untrusted sender.
    * **Post-Decryption:** If successful, display the message and then call `DELETE /api/messages/<message_id>` to delete it from the server.

6.  **User Logout:**
    * Call `POST /api/user/logout` to blacklist the JWT.
    * **Crucially, purge the ephemeral private key from browser memory.**
    * Clear the JWT from client-side storage.

7.  **General Client-Side Security:**
    * **Content Security Policy (CSP):** Implement strict CSP headers to mitigate XSS attacks by controlling allowed sources for scripts, styles, etc.
    * **Secure JavaScript Coding:** Avoid `eval()`, use templating engines that auto-escape output, sanitize all user-generated content rigorously before rendering it into the DOM.
    * **User Interface (UI) for Security:** Provide clear, user-friendly prompts and warnings regarding security actions (e.g., "Load your private key", "Unverified message").
